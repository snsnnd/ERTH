# ERTH 对战平台协议与机制（V2）

> **状态：BT 内 V2 协议层、平台状态机、UI/传输接入和嵌入式 C SDK 初版已实现。** 选手接线格式、字段、CRC 与安全行为以 [`PLAYER_PROTOCOL_V2.md`](PLAYER_PROTOCOL_V2.md) 为准。选手车辆固件接入及双车实车联调尚未完成；V1 继续可用，V2 未验收前不得用于正式对局。

## 1. 目标与边界

BT 从“串口/蓝牙调试工具”演进为**对局主机**：负责建局、车辆身份与角色、比赛状态、命令授权、心跳与掉线处理、地图/位置裁判、对手信息转发、事件记录和最终结果展示。

协议不假定现有车辆具有尚未确认的寻宝、碰撞、生命值或计分传感器。V2 提供通用 `EVENT` / `SCORE` 扩展点；具体胜负条件和计分算法须依据比赛规则另行确认。

## 2. 现有 V1 的边界

目前固件和 `final.py` 主要通过换行文本通信：

- 车辆上报 `POS:`、`RPOS:`、`PID:`、`track_data:` 等；平台校验 `RPOS:` 后向另一车转发 `ORP:`，不通过时回发 `ERR:RPOS,`。
- 控车命令是 `DRV:`、`STOP`、`ESTOP`、`AUTO`、`START` 等纯文本行。
- SPP 车辆链路通过 Car A/B 串口；BLE 链路另行连接。BLE 收到的数据目前只进日志，不与 A/B 对局状态、地图和裁判数据统一。

V1 可用于调试，但缺少统一身份/比赛会话、帧校验、消息序号、命令确认与去重、统一链路状态及明确的比赛状态机。位置和命令也无法可靠区分旧局重放、乱序或重复消息。V2 解决这些机制问题，不把 V1 的字段名直接当成新协议。

## 3. 平台架构与权威边界

协议与传输分层，串口和 BLE 只负责字节搬运：

1. **Transport Adapter**：SPP 虚拟串口、BLE UART；完成分片/粘包处理，不理解比赛规则。
2. **Frame Codec**：V2 帧解析、长度/CRC 检查、序号去重。
3. **Session Manager**：HELLO/WELCOME、车辆身份、会话号、心跳、在线状态与重连。
4. **Match Engine**：比赛状态机、角色分配、命令授权和事件时间线。
5. **Referee**：地图版本、位姿/申报位置校验、裁决和对手信息转发。
6. **UI**：建局、准备/开始/暂停/终止、逐车启停与急停、模式选择、地图、状态灯、告警、遥测和结果；UI 按钮不得绕过 Match Engine 直接写串口。

**平台是比赛状态与裁决的唯一权威。** 车辆可报告传感器/位姿和申报位置，但不能直接给对手下发可信数据，也不能自行宣布比赛开始、接受裁决或修改比赛角色。平台对 A、B 两车使用同一套帧和状态机。

**平台也是车辆控制的唯一入口。** 操作员在 UI 选择目标车并执行启停、软停、急停/复位、自动/手动切换、目标点设置或手动驾驶；所有操作先经过 Match Engine 做状态/权限校验，再转换为 V2 消息发给车辆，不允许 UI 直接写串口或 BLE。正式比赛的 START/PAUSE/RESUME 是整场控制；BENCH 练习模式可以单独启停选中的车辆。

## 4. 传输与帧格式

### 4.1 传输参数

- SPP UART：115200、8N1；BLE UART 使用同一字节流协议。
- 一帧一行，以 `LF` 结束，兼容接收端剥除 `CRLF`。
- BLE 写入可按协商 MTU 分成多个写操作；接收端必须按字节流重新组帧。分片边界不代表消息边界。
- 最大帧长暂定 **128 字节（含校验及行结束符）**，超过即丢弃整帧并重新同步。

### 4.2 V2 信封

```text
@2,<sid>,<src>,<dst>,<seq>,<type>,<field1>,...*<crc16>\n
```

| 字段 | 规则 |
|---|---|
| `2` | 协议主版本。未知主版本必须拒绝，不能猜测解析。 |
| `sid` | 16 位十六进制字符的 64-bit 会话号。握手前为全零；WELCOME 后本局固定。 |
| `src` / `dst` | `HUB`、`A`、`B`。身份由平台会话分配，不由车辆上报字段自行声明。 |
| `seq` | 8 位十六进制、32-bit 发送序号；每个发送端在会话内递增，允许回绕。 |
| `type` | 固定消息类型。字段数量和类型由消息定义决定。 |
| `crc16` | 4 位十六进制 CRC-16/CCITT-FALSE，覆盖 `@` 后第一个 `2` 到 `*` 前一个字节，不含 `@`、`*` 和换行。参数：poly `0x1021`、init `0xFFFF`、反射关闭、xorout `0x0000`。 |

载荷使用 ASCII 和固定字段，不允许逗号、`*`、`@` 或任意日志文本嵌入字段。错误日志使用有限错误码；需要扩展内容时增加有版本定义的字段，不能临时拼自由文本。

示例（CRC 仅作占位，实际必须计算）：

```text
@2,7B42E19A03D50211,HUB,A,00000011,CMD,DRIVE,300,300,400*<CRC16>\n
@2,7B42E19A03D50211,A,HUB,0000007A,ACK,00000011,OK*<CRC16>\n
@2,7B42E19A03D50211,A,HUB,0000007B,POSE,9300,3900,0,5120*<CRC16>\n
```

流解析器必须支持任意分片/粘包；长度溢出、字段错误或 CRC 错误时丢弃当前帧并从下一个 `@` 重新同步。CRC 用于检测传输损坏，**不是身份认证或防作弊机制**。

## 5. 会话建立与身份

1. 上电及断线重连时车辆必须停车；车辆发送 `sid=0000000000000000` 的 `HELLO`，包含固件版本、每次启动变化的 `boot_id`、能力位和传感器数量。握手前的 `HELLO` 序号从本次启动的 0 开始；此时不得接受运动命令。
2. 平台将链路绑定到配置好的物理车辆（A 或 B），检查协议版本/能力后发送 `WELCOME`，分配新的 `sid`，并下发角色、地图版本、心跳周期、命令租约上限和对局模式。`WELCOME` 是新会话的第一帧，接收后车辆在新 `sid` 下从序号 0 开始发送。
3. 车辆校验配置后发送 `READY`；平台用 `ACK` 确认接受，或用 `NACK` 拒绝并给出原因。平台只有在地图已加载且本局要求的所有参赛车辆均 READY 时，才允许从 PREPARING 进入 RUNNING。
4. `sid` 不匹配的帧一律拒绝并要求重新握手，不用旧会话回 NACK。重启、重连或新局必须使用新会话号；旧会话的位姿、命令和对手信息不得复用。
5. A/B 是平台配置的参赛者身份，角色在 PREPARING 阶段分配，RUNNING 后不能通过车端命令改写。

建议的能力位：`DRIVE`、`POSE`、`CLAIM`、`SENSOR8`、`SPEED`。双方协商能力交集；没有对应硬件的能力不得宣称支持。

## 6. 消息目录

所有消息都带统一信封。下表列的是 `type` 和其后固定顺序的载荷字段。

| 类型 | 方向 | 载荷与用途 |
|---|---|---|
| `HELLO` | A/B → HUB | `fw,boot_id,caps,sensor_count`；连接或重启声明。 |
| `WELCOME` | HUB → A/B | `role,map_version,hb_ms,lease_ms,mode`；接受接入并给出本局配置。 |
| `READY` | A/B → HUB | `status`，`OK` 或 `NOT_READY_<reason>`；车端初始化完成或报告未就绪原因码。 |
| `MATCH` | HUB → A/B | `PREPARE / START / PAUSE / RESUME / ABORT / FINISH,reason`；只能按状态机合法迁移。 |
| `CMD` | HUB → A/B | `START`（仅 BENCH 单车启动）、`DRIVE,left_pwm,right_pwm,lease_ms`、`STOP`（目标车软停）、`ESTOP`、`ARM`、`MODE,AUTO|MANUAL`、`TARGET,x10,y10`。只有有能力且当前状态允许的固件才能接受对应动作；官方比赛中禁止绕过整场 MATCH 状态单独 START 一辆车。 |
| `ACK` | 双向 | `ref_seq,result`；确认某条需要确认的命令/请求。 |
| `NACK` | 双向 | `ref_seq,error_code`；拒绝命令，例如 `BAD_STATE`、`BAD_RANGE`、`ESTOP_LATCHED`、`UNSUPPORTED`。旧 `sid` 帧直接丢弃并要求重新握手，不以 NACK 响应。 |
| `HEARTBEAT` | 双向 | `PING/PONG,uptime_ms,state`；链路保活，不代替驱动租约。 |
| `STATE` | A/B → HUB | `car_state,control_mode,role,flags`；车端权威运行状态回报。 |
| `POSE` | A/B → HUB | `x10,y10,yaw_mdeg,uptime_ms`；车辆估计位姿，仅作裁判输入之一。 |
| `CLAIM` | A/B → HUB | `x10,y10,uptime_ms`；车端申报/策略位置，明确标为不可信，取代 V1 `RPOS:`。 |
| `VERDICT` | HUB → A/B | `claim_seq,ACCEPT|REJECT,reason`；平台对一条 CLAIM 的裁决。 |
| `OPPONENT` | HUB → A/B | `opponent_id,x10,y10,claim_seq,age_ms`；只转发裁决通过且仍新鲜的申报位置，取代 V1 `ORP:`。 |
| `SENSOR` | A/B → HUB | `line_mask`；可选 8-bit 循迹快照，2 位十六进制；bit 定义由硬件配置版本固定。 |
| `SPEED` | A/B → HUB | `left_mmps,right_mmps`；可选车轮速度遥测，单位 mm/s。 |
| `EVENT` | A/B → HUB | `event_code,value`；车端事件。只能报告观测，不直接加分。 |
| `SCORE` | HUB → A/B | `team_a,team_b,reason`；平台裁决后的比分快照。计分规则由比赛规则配置定义。 |

坐标固定用十分之一地图单位（例如 `9300` 表示现有地图坐标 `930.0`）；航向单位为毫度，范围归一到 `[-180000,180000]`。这样保留当前地图精度，避免浮点文本格式不一致。`uptime_ms` 是发送端单调时钟，仅用于同一启动周期内的顺序/诊断；平台新鲜度使用本地接收时间，不假定两端时钟已同步。

## 7. ACK、序号、重发与流控

- 序号按发送端独立递增。接收端在同一 `sid` 内对重复 `seq` 去重；重复的需确认命令不得重复执行，但必须重发原 ACK。新旧序号按 32-bit 模数顺序比较，半序号空间以外的帧视为过期。
- 除周期刷新流 `CMD,DRIVE` 外，所有改变比赛状态或车辆状态的 `CMD`、`MATCH` 均需 ACK/NACK；`READY` 也需平台确认。`WELCOME` 由 `READY` 完成握手确认；ACK 的 `ref_seq` 是原帧完整的 8 位十六进制 `seq`，响应须使用相同 `sid`。ACK/NACK 本身不再确认。
- 超时重发使用**相同 `seq` 和相同帧内容**，最多 3 次；超过后报告链路故障。不能把同一命令重发时分配新序号。
- `DRIVE` 是带租约的周期刷新命令，每次刷新使用新序号；平台约每 100ms 刷新。车辆在 `lease_ms` 到期后清零电机并保持停车，不得因超时自动切回 AUTO。
- 传感器/速度/位姿遥测采用最新值优先，拥塞时丢旧遥测，不得阻塞电机控制、心跳和 ESTOP。
- STOP/ESTOP 优先于普通运动命令。状态迁移中收到迟到的 DRIVE 必须拒绝。

## 8. 比赛状态机

```text
LOBBY → PREPARING → RUNNING ↔ PAUSED
          │             │        │
          └── ABORT ────┴────────┴→ FINISHED
任何活动状态 ────────────────────→ FAULT → 人工复位后 LOBBY
```

| 状态 | 允许行为 |
|---|---|
| `LOBBY` | 连接车辆、加载地图、选择模式；官方对局运动命令拒绝。只有显式选择 BENCH 后，才开放受单车安全状态约束的练习控制。 |
| `PREPARING` | 分配 A/B 与角色、协商能力/地图、等待所有必需车辆 READY；电机保持禁止。 |
| `RUNNING` | 接收规则允许的控制与遥测；只有 HUB 可开始/暂停/结束。 |
| `PAUSED` | HUB 向所有在线车辆发 STOP；不接收 DRIVE，直到显式 RESUME 且链路健康。 |
| `FINISHED` | 正常结束或 ABORT；禁止运动，保存结果、事件和最后状态。 |
| `FAULT` | 校验/裁判/硬件/链路故障；默认停车并要求人工处理，不能静默恢复。 |

ABORT 仅由 HUB 在 PREPARING/RUNNING/PAUSED 发起并进入 FINISHED；FAULT 需要人工复位后回到 LOBBY。START 只允许 PREPARING，RESUME 只允许 PAUSED；它们是整场命令，HUB 仅在所有必需车辆 ACK 且链路健康时才将本地状态标为 RUNNING。若 START/RESUME 部分车辆未确认，HUB 立即向在线车辆发 STOP 并进入 FAULT，不得把比赛记为正常开始/恢复。PAUSE 会使整场停车；在 RUNNING 中对单车执行 STOP 或该车触发 ESTOP，也默认立即 PAUSE 整场并停车另一辆车，避免一车继续比赛。PAUSE/STOP 未获确认也按故障处理。

任一参赛车辆失联、报告 ESTOP、地图版本不符或裁判输入不可用时，官方对局默认整体进入 PAUSED/FAULT 并停车两车。ESTOP 导致 PAUSED 后，必须先由操作员显式 ARM 清除锁存，再满足 RESUME 条件；ARM 不能从 RUNNING 清除急停。**练习/桌面直控**是独立的 `BENCH` 模式，不计入官方比分；车辆在 BENCH 下按单车独立启停，但沿用准备、运行、暂停、停车和急停门控，不改变官方比赛状态。是否允许 BLE 单车直控及比赛期间是否允许人工驾驶仍须确认，不能因 UI 选择了 A/B 就绕过比赛状态机。

## 9. 裁判机制与对手数据

1. HUB 将每车 `POSE` 作为位置合理性检查输入，将 `CLAIM` 作为不可信的对外申报；二者不能混为一个“真实位置”。
2. 校验 `sid`、序号、字段范围、申报新鲜度、该车在线状态、地图版本和当前 POSE 新鲜度后，才执行图上距离规则。
3. V1 当前规则是申报位置与车辆位置的图距离最多 2 跳；V2 暂提议沿用为配置项 `claim_max_hops=2`，不是写死在协议帧中。
4. 缺地图、图不连通、位姿过期、无法匹配节点时必须拒绝或暂缓裁决，返回明确原因；**不得退化为欧氏距离估算后自动放行**。这是 V1 当前“降级放行”需要收紧的地方。
5. 裁决通过后 HUB 发 `VERDICT ACCEPT` 给申报车，并只向对手发一条 `OPPONENT`。拒绝则发 `VERDICT REJECT`，不转发。对手信息超过 5 秒未刷新即失效，车辆不得继续使用旧值做新决策。
6. 对局日志保存原始帧、裁决原因、地图版本、接收时间和源序号，便于复盘；日志不参与实时控制。

## 10. 控车安全与在线判定（建议初值）

- 上电、重连、换局、PAUSED、FINISHED、FAULT：`motion_enable=0`，输出停车。
- 官方模式只有 HUB 在合法状态下向所有必需车辆发 `MATCH START` 后才能使能运动；BENCH 模式由 HUB 对已 READY 的选中车辆依次执行 ARM（如有急停锁存）和 `CMD START`。`CMD START` 仅在 BENCH 接受，且不能绕过急停、就绪或租约门控。
- `DRIVE` 速度限幅 `-999..999`，租约不得超过 400ms；建议平台 100ms 刷新。超过租约停车并保持当前模式为 MANUAL。
- `STOP` 为可恢复软停车；`ESTOP` 为锁存停车，任意状态均允许。只有操作员经 HUB 发 `CMD,ARM` 才能清除锁存；车辆仅在 LOBBY/PREPARING/PAUSED 或 BENCH 停车态且电机已停车时接受 ARM，RUNNING 时拒绝。ARM 本身不启动电机；官方模式之后仍须合法的 MATCH START/RESUME，BENCH 则须由 HUB 发 `CMD START`。
- 心跳建议每 250ms；连续 1 秒没有有效帧，HUB 将该车标为 OFFLINE。驱动租约仍独立执行，不能依赖 HUB 的 1 秒离线判定来停车。
- 对局中一车离线默认 PAUSE 两车；重新连接需重新握手并 READY，不得直接恢复旧 DRIVE。
- CRC 和随机会话号不能防止主动伪造。若对手可接入无线链路，需另行设计配对/白名单及带密钥 MAC；未配置密钥时，UI 必须标明“链路校验不等于防作弊”。

## 11. 从 V1 迁移到 V2

1. 冻结 V1 字段与命令，作为调试/兼容模式，不继续增加比赛功能到散落的字符串分支中。
2. 先实现独立 Codec 与黄金帧测试：CRC、截断、粘包、超长、重复序号、回绕、错误版本。
3. 单车联调 HELLO/WELCOME、session、ACK/NACK、心跳和死区停车；架空轮测试 DRIVE/STOP/ESTOP。
4. 加入双车 Match Engine、状态机和统一 transport adapter；BLE 收发也进入同一个帧路由/比赛数据模型，不再只记日志。
5. 加入裁判 V2，默认 fail-closed；运行一段只读影子模式，对比 V1 判定但不驱动车辆。
6. 两车完整验收后才允许官方模式；V2 握手后禁止同一链路悄悄退回 V1，避免状态/身份混用。
7. 根据比赛规则实现计分插件和结果封存；规则确认前仅显示事件与裁决，不自行推断胜负。

## 12. 需要确认的规则参数

以下采用的是提议初值，不是已批准的竞赛规则：

1. 正式比赛角色名称、角色能做的动作、胜负/计分条件，以及是否需要人工驾驶。
2. 是否保留 V1 的申报位置最大 2 跳规则；失联/暂停后的恢复要求。
3. 官方对局必须双车在线，还是允许单车练习模式；BENCH 模式是否允许 BLE 单车直控。
4. 心跳 250ms、OFFLINE 1s、位置过期 5s、DRIVE 租约 400ms 是否满足场地/无线链路。
5. 是否需要对抗主动伪造；若需要，密钥如何配置/保存以及是否允许 BLE 未配对连接。
